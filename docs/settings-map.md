## Notes

- One schema id maps to exactly one dconf path. Key names may repeat across
  schemas (e.g. `cpu-refresh-time` in both system-monitor schemas) but they are
  independent settings under different paths — no conflict.
- `system-monitor` (old, 107 keys) is kept only for one-shot migration into
  `system-monitor-next-applet` (see `subsystems/system-monitor/migration.js`).
  Runtime reads the `-next-applet` schema exclusively.
- Files under `migrations/schemas/` are legacy shims read once by `migrations.js`
  (`panel-clone`, `topbar-panel-controls`, old `gnome-customizer-manager`).
  Do not add new keys there.
- Per-monitor / per-hardware keys keep upstream defaults, never snapshotted:
  `panel-element-positions`, `panel-lengths`, `panel-anchors`,
  `panel-visible` (connector-id JSON) and `primary-monitor` (empty = auto).
  A fresh machine generates its own layout for its own monitors.
- `migration-*` guard keys in the suite schema keep default `false` so fresh
  installs re-run migrations.
